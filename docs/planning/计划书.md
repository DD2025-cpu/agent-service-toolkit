# 四、先审核现有模型，不能直接塞进去

模型接入前必须完成一次“模型体检”。

这是整个计划最重要的检查点。

## 需要检查的内容

### 1. 模型输入特征

你当前模型可能包含：

- `capacity`
- `investment`
- `full_hours`
- `tariff`
- `opex_ratio`
- `province`

需要明确每个字段：

- 中文含义；
- 数据类型；
- 单位；
- 取值范围；
- 是否允许为空；
- 是否参与模型训练；
- 训练时的特征顺序。

### 2. 单位问题

你的历史数据中，电价可能是：

```text
1200～1800
```

这很可能是越南盾/kWh。

但中国油田风电电价可能使用：

```text
0.2～0.5元/kWh
```

不能把`0.35元/kWh`直接传给一个使用`越南盾/kWh`训练的模型。

必须建立单位转换和特征说明文件，例如：

```text
外部输入：yuan_per_kwh
模型输入：vnd_per_kwh
转换方式：根据明确汇率转换
```

更好的方法是后续统一为人民币单位并重新训练模型。

### 3. IRR目标是否由输入公式直接生成

如果训练数据中的IRR就是通过以下变量计算得到：

- 投资；
- 电价；
- 利用小时；
- 运维成本率；

然后又用这些相同变量训练XGBoost预测IRR，那么模型其实是在近似一个已经确定的计算公式。

这在论文中可能被质疑：

> 既然IRR能够直接计算，为什么还要用机器学习预测？

必须在模型接入前确定解释方式。

比较稳妥的处理是：

- 经济指标工具负责精确计算IRR；
- XGBoost负责快速预评价、经济等级预测或不确定条件下的预测；
- 如果数据条件允许，进一步让XGBoost预测年发电量、利用小时或运维成本等不确定变量；
- 再把预测结果传给现金流工具计算IRR。

成功标志：

> 可以明确说明“什么由公式计算，什么由机器学习预测，以及为什么需要机器学习”。

# 六、旧代码提取规则

每个旧函数都要满足以下要求。

## 1. 不允许写死文件路径

错误示例：

```python
data = pd.read_csv(r"E:\F_WorkSpace\xxx\data.csv")
```

改造后：

```python
def load_data(file_path: str):
    ...
```

## 2. 不允许依赖全局变量

错误示例：

```python
result = capacity * tariff * full_hours
```

其中变量来自Notebook上方单元格。

改造后必须明确传参：

```python
def calculate_revenue(
    capacity_mw: float,
    tariff_yuan_per_kwh: float,
    full_load_hours: float
) -> float:
    ...
```

## 3. 核心计算函数不直接打印

错误示例：

```python
print("IRR为：", irr)
```

改造后：

```python
return {
    "irr": irr,
    "npv": npv
}
```

## 4. 核心函数不直接生成自然语言

计算工具只返回数据：

```json
{
  "irr": 0.087,
  "npv_yuan": 12560000,
  "lcoe_yuan_per_kwh": 0.294,
  "payback_period_years": 8.3
}
```

最后由Agent解释。

## 5. 所有默认参数必须公开

不能在函数内部偷偷使用：

```python
discount_rate = 0.08
```

必须在结果中说明：

```json
{
  "assumptions": {
    "discount_rate": 0.08,
    "project_life_years": 20
  }
}
```

# 七、统一参数标准

第一版建立一个统一的项目参数对象。

## 基础必填参数

| 参数名                     | 中文含义     | 类型  | 单位    | 建议范围  |
| -------------------------- | ------------ | ----- | ------- | --------- |
| `installed_capacity_mw`    | 装机容量     | float | MW      | 大于0     |
| `unit_capex_yuan_per_kw`   | 单位投资     | float | 元/kW   | 大于0     |
| `full_load_hours_per_year` | 年利用小时   | float | 小时/年 | 0～8760   |
| `tariff_yuan_per_kwh`      | 上网电价     | float | 元/kWh  | 大于等于0 |
| `opex_ratio`               | 年运维成本率 | float | 比例    | 0～1      |
| `project_life_years`       | 项目运营期   | int   | 年      | 1～50     |
| `discount_rate`            | 折现率       | float | 比例    | 0～1      |

## 第一版可选参数

| 参数名                         | 中文含义       | 单位   |
| ------------------------------ | -------------- | ------ |
| `construction_years`           | 建设期         | 年     |
| `carbon_price_yuan_per_ton`    | 碳价           | 元/吨  |
| `emission_reduction_t_per_mwh` | 单位发电减排量 | 吨/MWh |
| `loan_ratio`                   | 贷款比例       | 比例   |
| `loan_interest_rate`           | 贷款利率       | 比例   |
| `residual_value_rate`          | 残值率         | 比例   |
| `annual_degradation_rate`      | 年发电衰减率   | 比例   |
| `province`                     | 项目所在地     | 文本   |
| `project_id`                   | 项目编号       | 文本   |

## 参数原则

- 外部接口统一使用人民币；
- 比例统一使用小数，例如8%写成`0.08`；
- 容量统一使用MW；
- 发电量统一使用MWh或kWh，内部明确换算；
- 不允许同一个字段有两种单位；
- 模型原始单位由适配器转换；
- 每次评价都要返回实际使用的参数和假设。

```json
  "query": "风电项目内部收益率评价标准",
  "top_k": 5,
  "filters": {
    "document_type": "policy_or_paper"
  }
}
```

输出示例：

```json
{
  "results": [
    {
      "document_id": "paper_012",
      "title": "文档标题",
      "content": "相关摘要",
      "page": 8,
      "score": 0.86
    }
  ]
}
```

禁止行为：

- 检索不到时编造来源；
- 没有文档依据却生成虚假引用；
- 用RAG结果代替经济指标计算；
- 将文献中的通用结论直接冒充当前项目结论。

# 九、六个工具的调用顺序

```text
1. validate_project_parameters
```

| 用户请求                | 应调用工具                   |

# 十、模型文件如何打包

不能只保存一个`model.pkl`就结束。

至少需要以下文件：

```text
artifacts
├── xgboost_model.json
├── feature_schema.json
├── training_manifest.json
├── model_metrics.json
└── model_version.txt
```

## `xgboost_model.json`

保存训练后的XGBoost模型。

优先使用XGBoost官方JSON格式，便于跨版本检查。

## `feature_schema.json`

记录：

- 特征名称；
- 特征顺序；
- 数据类型；
- 单位；
- 允许范围；
- 缺失值处理方式；
- 类别特征编码方式。

示例：

```json
{
  "features": [
    {
      "name": "capacity_mw",
      "type": "float",
      "unit": "MW",
      "min": 1,
      "max": 1000
    }
  ]
}
```

## `training_manifest.json`

记录：

- 数据来源；
- 数据量；
- 训练时间；
- 训练代码版本；
- 随机种子；
- 训练集和测试集划分方式；
- 是否包含增强数据；
- 数据使用的货币和单位；
- Python和XGBoost版本。

## `model_metrics.json`

保存：

- MAE；
- RMSE；
- R²；
- 交叉验证结果；
- 对比模型结果；
- 测试集样本数。

这四个文件共同证明模型不是一个来源不明的黑盒。

# 十二、测试计划

## 1. 经济计算测试

至少测试：

- 正常项目；
- 零电价；
- 极低利用小时；
- 极高投资；
- 无法计算IRR；
- 现金流始终为负；
- 投资回收期超过运营期；
- 小数和单位转换；
- 边界折现率；
- 不同运营年限。

要求：

> 确定性计算测试必须100%通过。

## 2. 模型测试

至少检查：

- 模型是否正常加载；
- 特征顺序是否正确；
- 缺失特征是否拒绝；
- 类别编码是否一致；
- 同一输入结果是否稳定；
- 超出训练范围是否警告；
- 模型版本是否返回；
- 与旧项目预测结果是否一致。

## 3. Agent测试

至少准备以下任务：

- 只问概念；
- 只要求计算；
- 只要求预测；
- 要求完整评价；
- 缺少参数；
- 参数单位错误；
- 要求情景分析；
- 要求说明原因；
- 要求政策依据；
- 工具执行失败；
- 模型API超时；
- Prompt注入；
- 用户要求编造结果。

# 十四、Git开发规则

建议只保留以下主要分支：

```text
main       稳定可演示版本
develop    日常集成版本
feature/*  单个功能开发
```

例如开发经济计算工具：

```bash
git checkout develop
git checkout -b feature/economic-tools
```

完成后：

```bash
git add .
git commit -m "feat: add wind project economic calculation tools"
git checkout develop
git merge feature/economic-tools
git push origin develop
```

建议功能分支：

```text
feature/parameter-schema
feature/economic-tools
feature/model-inference
feature/shap-explanation
feature/scenario-analysis
feature/rag-knowledge
feature/agent-workflow
feature/evaluation
```

不要第一天就把所有代码一次性提交。连续、真实的Git记录本身也是简历项目的证明。

- React重写；
- MySQL集群；
- Kubernetes；
- 复杂权限系统；
- 手机App；
- 语音；
- MCP大规模工具接入；
- 自动生成Word/PDF；
- 微服务拆分。

这些功能看起来高级，但会拖慢核心项目。等单Agent版本稳定后，再选择一两个增强点。





**里程碑一：工具Agent可以运行**
自然语言输入后，Agent能正确调用现有Python工具。

**里程碑二：软件页面可以演示**
Streamlit页面能完成输入、追问、计算、解释、情景和报告展示。

**里程碑三：项目可以量化验收**
50条评测集能够计算工具选择准确率、参数提取准确率、RAG引用准确率和端到端成功率。
